# 游戏功能文档质量检查

## 概述

本 skill 提供游戏功能文档的**质量检查、关联影响校验和跨文档自检**能力，确保文档质量和多文档之间的一致性。也被 `game_doc_generator` 主流程引用，在文档生成后执行质量检查。

---

## 模块A：文档质量检查清单

⚠️ **生成文档后必须执行**

在提交文档给用户之前，AI 助手必须对生成的文档进行以下检查。每项标注了适用的文档模式：

- 🔵 = 框架设计文档 + 开发文档均适用
- 🟢 = 仅开发文档适用

### 1. 规则完整性检查 🔵
- [ ] 是否包含开启条件、参与条件、循环规则、结束规则？
- [ ] 是否覆盖所有正常流程和异常情况？
- [ ] 是否有明确的边界条件处理（如上限、下限、满额等）？
- [ ] 特殊处理章节是否详细说明了各种异常场景？

### 2. 规则细节检查 🔵
- [ ] 每条规则是否有明确的触发条件和执行结果？
- [ ] 所有提到的参数是否都有具体数值或取值范围？
- [ ] 涉及计算的地方是否提供了公式和计算示例？
- [ ] 规则描述是否清晰无歧义？

### 3. 参数可配置性标注检查 🔵 ⚠️ 重点检查
- [ ] 规则中提到的所有参数是否明确标注了是"硬编码"还是"可配置"？
- [ ] 可配置参数是否注明"见配置表"或"通过配置表设置"？
- [ ] 硬编码参数是否直接给出了确定的数值？

### 4. 配置表一致性检查 🟢 ⚠️ 严格要求
- [ ] 规则中标注为"可配置"的参数，是否在配置表设计中有对应字段？
- [ ] 配置表中的每个字段，是否在规则说明中被引用和解释？
- [ ] 字段的数据类型（int/string/json等）是否匹配规则描述？
- [ ] 配置表的字段命名是否符合项目规范？

### 5. 数值需求检查 🔵
- [ ] 是否列出了所有需要配置的数值参数？
- [ ] 数值说明是否包含参数名称、取值、说明三要素？
- [ ] 是否区分了示例数值和最终确定数值？

### 6. 系统依赖检查 🔵（框架文档简化检查）
- [ ] 是否列出了所有依赖的系统模块？
- [ ] 是否说明了需要的接口功能？
- [ ] 依赖的系统是否在项目中已经存在（参考项目文档分析结果）？

### 7. 格式规范检查 🔵
- [ ] 标题层级是否正确（H1/H2/H3）？
- [ ] 表格是否有清晰的表头？
- [ ] 列表是否有合理的层级和缩进？
- [ ] 是否善用了表格来呈现结构化信息？

### 8. 术语统一性检查 🔵 ⚠️ 关键检查
- [ ] 文档中的功能和模块名称是否与项目已有术语一致？
- [ ] 相同的功能是否使用了统一的表述方式？
- [ ] 所有核心术语是否使用【】或""符号进行了标注？
- [ ] 是否避免了同一概念的多种说法（如金币/游戏币/货币）？

### 9. 配置表复用检查 🟢 ⚠️ 严格要求
- [ ] 是否检查了项目已有的配置表清单？
- [ ] 如果已有表可以满足需求，是否复用而不是创建新表？
- [ ] 如果需要增加数据或字段，是否明确说明在哪张表中操作？
- [ ] 如果创建新表，是否说明了为什么已有表无法满足需求？
- [ ] 是否使用【新建】【增加数据】【增加字段】等标注明确了配置表操作类型？

### 10. 禁止代码/伪代码检查 🔵 ⚠️ 关键检查
- [ ] 文档中是否完全没有代码块？
- [ ] 规则描述中是否没有if/else/for/while等编程语句？
- [ ] 是否没有函数调用形式（如"function()"）？
- [ ] 所有逻辑和规则是否都用自然语言、表格或列表描述？
- [ ] 数值计算是否使用数学公式而非代码语法？

### 11. 系统解耦检查 🔵 ⚠️ 核心架构检查
- [ ] 是否成功解耦了对象属性与触发机制？（不使用"普通道具、特殊道具"分类，而是用属性标签定义实体）
- [ ] 规则拆分是否足够细粒度，是否具备扩展新类型而不改底层的能力？
- [ ] 是否梳理了事件源（触发器）和结果（执行动作），而不是面条式流水账描述？
- [ ] 对限时活动的描述，是否正确"继承"了基础规则，仅写出增量（Diff）？
- [ ] 策划需求系统依赖中是否有预留"广播事件"和"外部接口"说明？

### 12. 客户端和服务器逻辑检查 🟢 ⚠️ 工程落地检查
- [ ] 是否明确划分了客户端和服务器各自的职责范围？
- [ ] 客户端逻辑是否覆盖了显示交互、本地验证、数据缓存三个方面？
- [ ] 服务器逻辑是否覆盖了数据持久化、业务验证、核心计算、数据同步四个方面？
- [ ] 是否列出了所有关键的C/S交互协议，并说明了触发时机、请求内容、响应内容？
- [ ] 是否考虑了断线重连和数据同步的处理方式？

**如果任何一项检查不通过，必须修正后再提交给用户。**

## 模块B：关联文档影响校验

⚠️ **修改文档后必须执行**

当用户**修改了某个已有文档**的规则时，AI助手（你）**必须**执行以下流程：

### 步骤1：识别修改范围

- 确认被修改的文档属于哪个目录（`框架/` 还是 `开发文档/`）
- 提取本次修改的核心变更点

### 步骤2：遍历同目录文档与会议规避 ⚠️

- 使用 `find_by_name` 工具搜索同目录下所有已有的功能设计文档
- 找出所有文档（排除当前正在修改的文档以及 `框架/游戏结构总览.md` 索引表）
- **历史会议记录同步规避原则**：在梳理影响扩散时，明确**绝对不将 `会议记录/` 目录下的档案**视为需要被牵连修改的目标。会议记录是客观发生的历史存照，任何关联同步都不应改写会议记录。

### 步骤3：逐文档分析关联性

对每个找到的文档，检查以下关联点：

| 检查项 | 说明 | 示例 |
|-------|------|------|
| 共享系统依赖 | 修改的规则是否影响了其他文档依赖的系统接口 | 修改了【背包系统】的容量规则，其他引用背包的文档可能受影响 |
| 共享配置表 | 修改的配置表字段是否被其他文档引用 | 修改了 `item_config` 表结构，其他使用该表的文档需同步 |
| 共享术语 | 修改的术语或命名是否在其他文档中出现 | 将【金币】改为【游戏币】，其他文档中的叫法需同步 |
| 规则继承 | 修改的基础规则是否被其他文档"继承" | 修改了物件的基础合成规则，限时活动中继承该规则的部分需同步 |
| 数值关联 | 修改的数值是否影响其他系统的平衡 | 修改了体力恢复速度，依赖体力的其他功能需评估影响 |

### 步骤4：生成关联影响报告

如果发现可能受影响的文档，向用户报告：

```
📋 关联文档影响分析：

本次修改了【当前文档名】中的以下规则：
- [修改内容摘要]

以下文档可能需要同步更新：

1. 【文档A名称】
   - 影响原因：共享了 xxx_config 配置表的 yyy 字段
   - 建议操作：同步修改该表字段的说明

2. 【文档B名称】
   - 影响原因：继承了本文档中的"基础合成规则"
   - 建议操作：检查增量规则是否仍然兼容

是否需要我设计关联文档的修改方案？
```

### 步骤5：设计修改方案并执行

- 用户确认需要同步的文档后，**先设计修改方案**提交给用户审阅
- 修改方案应包含：每个关联文档的具体修改内容和原因
- 用户确认方案后，逐个打开并修改
- 每个文档的修改同样需要通过质量检查清单
- 修改完成后，再次确认是否还有其他关联文档需要更新

### 步骤6：触发维护《游戏结构总览》 ⚠️ **最后必须执行**

如果本次执行了联动关联文档的成批修改并已落地定稿，必须执行最后一次收尾：
- 读取并更新 `框架/游戏结构总览.md`。
- 将导致本次关联修改的新增联通点、或是重大的资源流向分发改动，同步在全局总览蓝图树上，完成真正的闭环。

**关键原则**：
- ✅ **主动提醒**：即使用户没有要求，也必须主动检查关联影响
- ✅ **列出具体影响**：不是笼统地说"可能有影响"，而是指出具体哪条规则、哪个字段受影响
- ✅ **等待确认**：不要未经用户同意就直接修改其他文档
- ✅ **先设计方案**：修改关联文档前先提交修改方案给用户审阅
- ✅ **记录变更**：同步修改后，更新被修改文档的"最后更新"日期
- ✅ **全局收口**：切记在末尾通过修改《游戏结构总览.md》来进行最终的归口结项

## 模块C：跨文档规则自检

⚠️ **完成文档后必须执行**

当**完成一个新文档**（包括【开发文档】与【框架设计文档】）或**完成对已有文档的重大修改**后，AI助手（你）**必须**执行以下流程以校验规则遗漏与冲突：

> **重要约束**：即使是宏观视角的【框架设计文档】，也严禁在“核心逻辑闭环”、“核心资源卡点”以及“与其他系统交互关联点”上发生设定缺失。任何维度的规则遗漏必须被如实反馈给策划！

### 步骤1：遍历所有项目文档与规避逻辑

- 使用 `find_by_name` 工具搜索 `框架/` 和 `开发文档/` 目录
- 逐个阅读所有已有的功能设计文档，**自动规避对 `会议记录/` 以及 `复盘记录/AI经验学习库.md` 中内容的跨文档强行自检修正在判定（它们是指导标准，而非需校对文件）**。
- 重点关注规则说明和配置表需求章节

### 步骤2：规则遗漏检查

检查当前文档是否遗漏了应当覆盖的规则：

| 检查项 | 检查方法 | 示例 |
|-------|---------|------|
| 通用规则遗漏 | 其他文档中存在的通用处理规则（如断线重连、背包满、资源不足），当前文档是否也需要 | 其他文档都有"背包满时奖励转邮件"的规则，当前文档是否遗漏 |
| 系统接口遗漏 | 当前文档依赖的系统，是否遗漏了必要的接口说明 | 依赖了【任务系统】但没有说明需要哪些任务接口 |
| 配置表字段遗漏 | 规则中提到的可配置参数，是否都在配置表中有对应字段 | 规则中提到"冷却时间可配置"但配置表中没有对应字段 |
| 边界条件遗漏 | 其他文档中描述的边界条件，当前文档是否也有类似场景需要覆盖 | 其他文档都处理了"VIP额外次数"的情况，当前文档是否遗漏 |

### 步骤3：规则冲突检查

检查当前文档与其他文档之间是否存在规则冲突：

| 冲突类型 | 检查方法 | 示例 |
|---------|---------|------|
| 数值冲突 | 同一参数在不同文档中的取值是否矛盾 | 文档A说体力上限100，文档B说体力上限120 |
| 流程冲突 | 同一操作在不同文档中的处理流程是否矛盾 | 文档A说奖励直接进背包，文档B说奖励需手动领取 |
| 配置表冲突 | 同一配置表字段在不同文档中的定义是否矛盾 | 文档A定义 `reward_type` 为1=物品/2=货币，文档B定义为1=金币/2=钻石 |
| 术语冲突 | 同一概念在不同文档中的叫法是否不统一 | 文档A称"体力"，文档B称"精力"，实际指同一资源 |
| 规则未对齐 | 文档之间涉及同一系统的规则描述口径是否一致 | 文档A说"合成消耗1点体力"，文档B在引用合成时说"合成消耗2点体力" |
| 引用规则错误 | 文档中引用其他文档/系统的规则时，引用内容是否与原文一致 | 文档B写"根据【合成系统】规则，三合一产出高级物件"，但合成系统实际规则是"两两合成" |

### 步骤4：生成自检报告

将检查结果整理为报告，提交给用户：

```
📋 跨文档规则自检报告：

✅ 已检查文档数量：X 个

--- 规则遗漏清单 ---

以下规则在其他文档中存在，但当前文档可能遗漏：

| 序号 | 遗漏规则 | 参考文档 | 建议 |
|------|---------|---------|------|
| 1 | 背包满时奖励转邮件 | 拉霸机规则.md | 建议在特殊处理章节补充 |
| 2 | VIP额外参与次数 | 合合玩法设计.md | 建议在参与条件章节补充 |

--- 规则冲突清单 ---

以下规则与其他文档存在潜在冲突：

| 序号 | 冲突内容 | 当前文档 | 冲突文档 | 建议 |
|------|---------|---------|---------|------|
| 1 | 体力恢复速度 | 5分钟/点 | 3分钟/点（天气系统.md） | 请确认统一取值 |

--- 无问题项 ---
✅ 术语一致性：无冲突
✅ 配置表定义：无冲突

请策划自查以上遗漏和冲突，确认后我将协助补充完善。
```

### 步骤5：等待用户确认并补充
- 用户确认需要补充的遗漏规则后，逐条添加到文档中
- 用户确认冲突的解决方案后，同步修改相关文档
- 补充完成后，重新执行模块A的质量检查清单

**关键原则**：
- ✅ **全量遍历**：必须遍历目录下的所有文档，不能跳过
- ✅ **具体定位**：遗漏和冲突必须指出具体的规则条目和来源文档
- ✅ **不擅自修改**：只报告问题，等待策划确认后再修改
- ✅ **区分严重程度**：冲突是必须解决的问题，遗漏是建议补充的内容
